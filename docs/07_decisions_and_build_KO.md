## 0. 요약

- **확정할 것은 다섯 개(Q1~Q5)입니다.** 연구가 무엇을 주장하는지를 정하는 결정이라 연구자가 정해야 합니다. 나머지 기술 결정 13개(T1~T13)는 기본값을 정해 사전등록 파일에 적어 두고, 나중에 바꿀 수 있게 만듭니다.
- **"오류 0"인 환경은 만들 수 없습니다.** 규칙이 없던 세계는 관측되지 않기 때문입니다. 대신 다음 조건을 갖춘 환경은 만들 수 있습니다. 모든 숫자를 출처 파일·코드 버전·설정까지 거슬러 올라갈 수 있다. 오차마다 크기와 방향을 잰다. 규칙의 "끈 상태"는 결과를 보기 전에 고정한다. 이 Mac에서는 Elexon·NESO API가 열려 있어 데이터도 직접 받을 수 있습니다(4장).
- **오늘 확인한 사실 일곱 개가 로드맵을 바꿉니다(1장).** 가장 큰 것은 두 가지입니다. BM 실제 현금흐름을 전 유닛에 대해 받을 수 있습니다. 그리고 BM 순수익은 "큰 수 − 큰 수"라서 실제 수익 재구성의 정확도가 05 문서의 판단보다 낮습니다.

| T10 | 효율·열화 | 왕복효율 90.25%(C1과 같음). 열화는 두 값: C1 비교용 £0.5/MWh와 사이클 수명 기반 값(CAPEX ÷ 수명 사이클로 직접 계산) | £0.5는 매우 낮아 도매 위주 전략을 유리하게 만든다. 열화 비용은 규칙 순위를 바꿀 수 있음 | 왕복효율 85% |
| T11 | 해 품질 | HiGHS, MIP gap ≤ 0.01%. 시간 제한에 걸린 해는 결과표에서 빼고 따로 표시 | 프로토타입 `response_no_stack`이 gap 0.7%로 결과에 섞였음 | — |
| T12 | Shapley 플레이어 | 모든 국면에 같은 다섯 개: {빠른 주파수 상품 접근, 주파수 상품과 도매의 겹치기, SoE 규칙, 예비력 상품(BR/QR/SR) 접근, BM 접근}. 그 국면에 없던 규칙은 "기여 0인 플레이어"로 둠. CM은 분해 밖에서 더함 | 05 문서 2.2(2)의 "국면 간 Shapley 비교 불가" 문제 해결. 기여 0인 플레이어는 다른 플레이어의 Shapley 값을 바꾸지 않으므로 국면 간 같은 척도가 된다 | one-at-a-time, leave-one-out, 순서별 범위 함께 |
| T13 | 보정과 검증 분리 | 보정(채택률, 롤링 규칙 등)은 2024-12 ~ 2025-09, 검증은 2025-10 ~ 2026-09 | 같은 자료로 맞추고 검증하면 순환 논리 | 기간 바꿔 반복 |

## 4. 세부까지 정밀한 환경을 만들 수 있나

**결론: 만들 수 있습니다.** 다만 목표는 "오차가 없는 환경"이 아니라 **"오차가 숨지 못하는 환경"**입니다. 구성 요소는 일곱 가지입니다.

| # | 장치 | 무엇을 막나 | 구현 |
| --- | --- | --- | --- |
| E1 | **고정 환경** | "내 컴퓨터에서는 돌았는데" | `.venv` + 버전 고정 `requirements.lock`. 모든 실행이 같은 환경에서 돈다 |
| E2 | **데이터 출처 기록** | 어떤 파일로 낸 숫자인지 모름 | 이미 있는 `MANIFEST.csv`(sha256 포함)를 전 데이터로 확대. 결과 폴더마다 입력 파일 해시를 기록 |
| E3 | **사전등록 파일** | 결과를 보고 규칙 정의를 바꾸는 것(갈림길 문제) | `spec.yaml`에 국면, 규칙별 off 상태, 자산, 민감도 축을 적고 **결과를 돌리기 전에 git 태그**. 나중에 바꾸면 변경 이유를 기록 |
| E4 | **불변식 테스트** | 조용한 버그(에너지가 새거나, 블록이 어긋나거나) | 매 실행 후 자동 점검: 에너지 수지, 동시 충방전 0, 출력 여유, SoE, 서머타임 날 구간 수(46/50), EFA 블록이 상품 낙찰 구간과 일치하는지. 손으로 답을 계산할 수 있는 장난감 사례(4구간 배터리)로 엔진을 시험 |
| E5 | **검증 하네스** | 모델이 현실과 얼마나 다른지 모름 | 엔진(롤링, 전체 규칙) vs 실제 수익 재구성을 유닛·월별로 비교하는 고정 절차. 차이를 항목별(도매·EAC·BM)로 분해 |
| E6 | **오차 예산표** | "모델 오차 < 규칙 효과"를 확인할 방법이 없음 | 오차 출처마다 방향(+/−)과 크기를 추정해 표로 관리: 완전예측, 가격 수용자, MID 근사, 페널티 미반영, 열화, 주 단위 분할. 규칙 효과와 나란히 보고 |
| E7 | **실행 기록** | 같은 숫자를 다시 못 냄 | 결과마다 `run.json`: git 커밋, spec 해시, 입력 해시, 해법 상태, gap, 계산 시간 |

**이 컴퓨터에서 확인한 것**: Elexon(`data.elexon.co.uk`)과 NESO(`api.neso.energy`) API 모두 응답 200. 그래서 데이터 받기도 이 환경 안에서 할 수 있고, 받은 내역이 자동으로 기록됩니다.

**만들 수 없는 것**: 규칙이 없던 세계의 실제 수익, DA 가격(F6), 사업자별 실제 비용·페널티, NESO의 발령 판단 과정. 이것들은 오차 예산표(E6)에 "관측 불가" 항목으로 남기고, 결과를 범위로 내서 다룹니다.

## 5. 연구에 허점이 없으려면: 비판적 점검표

05 문서에서 다룬 것(가격 수용자, 켤 수 없는 규칙, 완전예측 편향, 국면 혼동)에 더해, 이번에 구현 관점에서 새로 찾은 허점입니다. 각 항목의 대응이 어디에 구현되는지 함께 적었습니다.

| # | 허점 | 왜 문제인가 | 대응 | 구현 위치 |
| --- | --- | --- | --- | --- |
| H1 | 실제 수익 재구성의 측정 오차 | BM 순수익이 큰 수의 차이(F3). 도매 쪽은 PN × MID로 근사하는데, 실제 거래 가격을 모름 | 도매 쪽을 MID와 정산가격 두 가지로 평가해 범위로 냄. Lakeside 등 몇 기는 상장 펀드 공시 수치와 대조 | `realized/` |
| H2 | 유닛 매핑 오류 | EAC 유닛(예: `ANSC-001`)과 BMU(예: `T_LKSDB-1`)는 이름 체계가 다르고, 집합 유닛(`AG-…`)은 여러 사이트를 묶음 | 매핑마다 신뢰 등급(확실/추정/불명)을 달고, 결과를 "확실"만 vs 전체로 두 번 냄 | `realized/units.py` |
| H3 | 표본 선택 | 공개 자료로는 BM 등록 배터리만 재구성할 수 있음. BM 밖 배터리의 도매 거래는 보이지 않음 | 모집단을 "BM 등록 배터리"로 명시. 엔진의 기준 자산도 BM 등록 유닛으로 두고, 비BM은 "BM 접근 off" 규칙으로 다룸 | spec |
| H4 | 보정과 검증의 순환 | 같은 기간으로 맞추고 검증하면 모델이 맞아 보임 | T13 기간 분리 | `validation/` |
| H5 | 갈림길 문제 | 국면 4 × 규칙 32조합 × 지속시간 × 정보 수준 × 민감도. 결과를 보고 고르면 원하는 이야기를 만들 수 있음 | E3 사전등록. 모든 조합 결과를 부록에 전부 냄 | `config/spec.yaml` |
| H6 | 국면 간 Shapley 비교 | 국면마다 플레이어가 다르면 같은 척도가 아님 | T12: 공통 플레이어 다섯 개 + 기여 0인 플레이어 | `attribution/` |
| H7 | 엔진 오류가 규칙 효과로 둔갑 | 예: 프로토타입의 BR 누락(F4)은 "BR 규칙 효과 0"으로 보였을 것 | 상품별 데이터 커버리지 표를 매 실행마다 출력. 상품이 있던 기간인데 가격이 비면 실행 중단 | `data/`, E4 |
| H8 | 열화 비용이 규칙 순위를 바꿈 | 열화가 싸면 도매 차익(사이클 많음)이, 비싸면 주파수 상품(사이클 적음)이 유리 | T10 두 값으로 모든 분해를 반복 | 민감도 |

## 6. 구현 계획

### 6.1 코드 구조 (새로 만듦, 프로토타입 `model/`은 비교용으로 보존)

```
gbess/
  config/spec.yaml     사전등록: 국면, 규칙과 off 상태, 자산, 민감도 축 (E3)
  timebase.py          UTC 30분 인덱스, EFA 블록, 서머타임 (T4)
  data/                가격(MID·정산가격), EAC(EAC 이전·EAC·BR 두 출처), BM 현금흐름, CM, 주파수
  realized/            실제 수익 재구성: 유닛 매핑(H2), 유닛·월 수익 패널(H1)
  engine/              자산, 규칙 레지스트리, MILP 조립, 해법, 주 단위 롤링 (T2, T5)
  attribution/         one-at-a-time, leave-one-out, Shapley, 순서별 범위 (T12), 사건연구
  validation/          엔진 vs 실제 수익, 오차 예산 (E5, E6)
  finance/             ①→② 변환, 연간화, cap-and-floor 오버레이 (Q2 A+, Q5)
tests/                 불변식, 장난감 사례 (E4)
```

### 6.2 순서 (결정과 무관한 것부터)

| 순서 | 할 일 | 결정 의존 | 끝났다는 기준 |
| --- | --- | --- | --- |
| 1 | 고정 환경(E1), 시간축(T4)과 테스트 | 없음 | 서머타임 날 테스트 통과 |
| 2 | 데이터 층: EAC 두 출처 합치기(F4), EAC 이전 변환(P2), 커버리지 표(H7) | 없음 | 상품별 기간·결측 표 |
| 3 | BM 현금흐름 전 유닛 받기(F1) | 없음 | `MANIFEST` 기록, 배터리 유닛 월별 순 BM 수익 |
| 4 | 실제 수익 재구성(EAC + BM + 도매 근사), 매핑 신뢰 등급 | Q4(지역 열 추가 여부) | 유닛·월 패널, Lakeside 현금흐름과 일치 |
| 5 | 엔진(완전예측, 주 단위), 장난감 사례 테스트 | Q2(지속시간 목록) | 불변식 통과, 프로토타입과 같은 설정에서 차이 설명 |

| 8 | 공급곡선·사건연구 | Q1 (b)일 때 | 범위의 상한·하한 |
